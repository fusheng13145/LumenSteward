## 第 1 章 项目概述

### 1.1 项目定位

衔光管家（Clawbot）定位为：**微信原生的单拥有方「个人 / 家庭执行型智能管家」**——一个装好即用、深读你的微信世界、能主动把事办了的专属助手。

核心特征：

- **微信原生入口**：以微信公众号 / 企业微信为唯一交互面，直接消费微信上下文（消息、群聊、文件、收藏、通讯录标签）。
- **执行型而非纯对话型**：核心目标是"把事办了"——记忆用户偏好、跨会话管理任务、主动提醒与跟进。
- **单拥有方、自治部署**：面向个人 / 家庭 / 小社群主理人，实例私有、数据私有，不依赖任何中心化平台。
- **主动触达**：通过微信模板消息 / 订阅通知 / 群@ 等能力，在无需用户发消息时也能行动。

> 与"通用对话助手"的本质区别：通用对话助手是"你问它答"；衔光管家是"你不用问，它替你记、替你盯、替你办"的私人执行体。现实对标范式是个人 Agent 的自主执行，而非聊天机器人。

### 1.2 目标用户与价值

| 用户 | 典型场景 | 衔光提供的价值 |
|---|---|---|
| 个人用户 | "把刚才群里说的聚餐时间记下来，到点提醒我" | 读群上下文 + 主动推送提醒 |
| 家庭 / 宠物主 | "记下猫咪疫苗下一针日期，提前一周提醒" | 长期记忆 + 微信订阅通知 |
| 小社群主理人 | "每周一把本周安排汇总发到群里" | 群@ + 定时触达 + 微信内动作 |
| 自由职业者 | "把文件传输助手的发票整理成记账" | 读取微信文件 / 收藏 + 结构化档案 |
| 隐私敏感用户 | "我的对话和档案只能在我自己的服务器" | 单拥有方自治部署，数据不出私域 |

价值主张：**把微信从"聊天工具"升级为"私人执行中枢"**——对话只是控制面，行动才是主产品。

### 1.6 重新定位说明（演进记录）

本项目早期基线（迭代 1~3）实现的是一个"微信对话助手内核"（LLM 中枢 + 工具 + 审计 + 限流 + 归档 + 配置 + 回放 + 多模型）。为使产品定位清晰、避免与"通用对话助手"同质化，项目完成一次**定位重锚**：

- **从**：通用对话助手（你问它答）。
- **到**：微信原生的私人执行型管家（你不用问，它替你记、盯、办）。

重锚后的目标架构在既有内核之上增加**三层执行体能力**（个人状态库 / 事件与触发引擎 / 主动执行器，均属规划·迭代 4），使系统从 turn-driven 转为 event-driven。既有内核（迭代 1~3）全部可复用，无需重写。

重锚同时确定了一件事：**外部参照不改变定位**。同一项目命题存在多个小组的并行实现，其复盘记录里"能力更多"的部分（信息聚合工具、娱乐场景）恰恰是重锚要远离的方向；因此这类记录一律经 [7.7 轨道 C](#轨道-c外部母本能力对照同源项目其他小组的实现记录) 的五判据准入，判据第一条即本节的定位（ADR-012）。

## 第 2 章 核心功能说明

> 章节前缀「已实现」表示有对应 `main` 源码与测试；「规划」表示重新定位后的下一阶段目标，未实现。

### 2.1 微信通道接入（已实现）

- **单一入口**：`interfaces/wechat/WechatController`（含 `WechatCallbackController`），路径 `/wechat/callback`；在 `SecurityConfig` 中 `permitAll()`，由 `WechatSignatureVerifier` 执行平台验签。
- **验签与去重**：sha1 字典序签名；±300s 时间窗；同 `MsgId` 幂等去重（Redis `dedup:msg:{msgId}`）。
- **消息路由**：`MessageDispatcher` 单一入口 + 类型参数化路由（text/image/voice/location/event 策略族）。
- **先回执后推送**：回调 ≤700ms 内返回回执，终态经有界线程池异步推送（BR-06）。
- **token 管理**：缓存前缀分域 + 提前过期 + 分布式锁 + 单次失效重试（SRS 9.4.6）。
- **Mock 与真实通道复用同一 Controller 与同一段验签代码**。

### 2.2 对话与模型中枢（已实现）

- **Agent Loop**：`AgentOrchestrator`（`AgentOrchestratorImpl`）执行多轮工具编排，受 SC-01~SC-05 状态机硬约束（轮次 / 并发 / 超时）。
- **分发门控**：`MessageDispatcher` 分发前经 `UserStatusGate` 拦截禁用用户（不触发 LLM）。
- **模型调用**：经 `LlmClient` 抽象；`LlmClientRouter` 运行时多 provider 路由（见 2.10）。
- **上下文**：`ContextStore` 端口 + token 裁剪，保持 tool/assistant 消息配对不变式（SRS 9.4.4）。
- **实时观测（FR-08）**：编排过程事件经事件总线推送至 SSE 通道 `/api/sse/console`（详见 2.12）。
- **系统人设**：预置"衔光"人格，零配置。

### 2.3 AI 工具（Function Calling）（已实现）

工具位于 `domain/tool/impl`，统一实现 `Tool` 接口（`name()` / `description()` / `parametersSchema()` / `execute()`，另有 `idempotent()` / `critical()` / `readOnly()` 与三件自述元数据），由 `ToolRegistry` 构造器注入后**注册即暴露**进 LLM 函数 Schema。当前内置 6 个：

| 工具类 | 能力 | 备注 |
|---|---|---|
| `RecognizeImageTool` | 图片视觉识别（FR-10） | 语义 `recognize_image` |
| `SynthesizeVoiceTool` | 语音生成与发送（FR-11） | 语义 `synthesize_voice` |
| `QueryExpressTool` | 快递查询（FR-12） | 语义 `query_express` |
| `PlanRouteTool` | 导航服务（FR-13） | 语义 `plan_route` |
| `ManagePetProfileTool` | 宠物档案管理（FR-14） | 声明 `readOnly()` 支持回放护栏 |
| `QueryWeatherTool` | 天气查询（FR-23 **示例插件**） | 自包含样例数据集、结果标注 `data_source=mock-demo`；**默认由 `orchestration.disabled-tools` 灰度关闭**（V1.0.14） |

- 工具调用全程审计（`log_tool_call`，`call_seq` 递增）。
- 外部集成类工具为衔光自主实现，作为执行循环内部能力，不对外开放为市场。
- 「新增工具不改对话引擎」的契约、派生口径的反查方式与启动期 Fail-Fast 见 §2.24。
- **局限（如实标注）**：注册即暴露 = **无"出现条件"**——`ToolRegistry` 收录的工具每轮全量进入 LLM 函数 Schema，不随上下文（是否刚发过图片、对应 SPI 是否可用、是否被灰度关闭）裁剪。外部母本 M-2 在 39 工具规模下实证了"工具多了模型同样会选错"，而 W8 还将新增 5 个动词工具，故该缺口判为轨道 C 首位（W10，见 §7.7）。


### 2.4 反幻觉与一致性校验（已实现）

- **执行一致性校验**：`ConsistencyChecker`（`RuleBasedConsistencyChecker`）+ `ActionClaimExtractor`——当模型声称"已完成某动作"但无对应工具执行记录时，判定 `CLAIM_UNSUPPORTED` 并拦截（FR-09）。判定词表**不在此类里硬编码**：由每个工具 `claimKeywords()` 自述、`ToolRegistry` 汇总反查（FR-23，见 §2.24）。
- **内容安全 Fail-Closed**：`ContentSafetyService` 词库不可用时按 Fail-Closed 处理。
- **兜底文案**：模型不可用或越界时返回受控兜底话术（可由后台热改）。
- **目标**：执行性幻觉对外泄漏 = 0（迭代 2 已构造 ≥20 泄漏场景验证，全部拦截留痕）。

### 2.5 审计与安全基线（已实现）

- 全量敏感操作写入 `log_audit`（增删改、用户启停、配置变更、回放等），前后值留痕（`before`/`after`）。
- 越权访问返回 403 并落痕；出参统一脱敏（`interfaces/assembler`，手机号 / OpenId）。

### 2.6 限流与成本预算（已实现）

- `RateLimitDecision` 枚举化决策；用户 / IP 双令牌桶 + 白名单豁免 + Fail-Open（FR-20）。
- `CostBudgetServiceImpl` 成本预算控制；限流事件落 `log_rate_limit`。
- 预算的**逐笔明细与可视化消耗**（`log_llm_call` + `/api/cost/*` + `/cost` 看板）见 2.25；降级判定按"今日计数桶 / 当前生效预算"实时计算，标志位只用于日志去重。
- 设计约束：多构造器 Bean 须显式标 `@Autowired`（见 6.2）。

### 2.7 数据保留与归档（已实现）

- 180 天清理策略；细粒度删除与匿名化（FR-19）。
- `DataRetentionServiceImpl` 实现清理；保留索引覆盖 `wx_message` / `wx_session` / `log_tool_call` / `biz_pet_profile` 常用检索列。
- `log_llm_call`（W5 新增）同样在清理与删除范围内：按 180 天清理，用户删除时按其**脱敏 openid** 匿名化本表列（见 2.25）。

### 2.8 在线配置热生效（已实现）

- `DynamicConfigService`（接口）+ `DynamicConfigServiceImpl`（三级缓存读取 + 类型解析 + 降级回退，永不抛异常）。
- `ConfigAdminService`：类型校验 → 落库 → 缓存失效 → 审计；非法值被拒（400）；密钥落审计时遮罩。
- 编排器、兜底文案、strict-mode、fail-closed 等改为运行时读取，免重启生效（FR-18）。

### 2.9 回放调试台（已实现）

- `ReplayService`：工具调用干跑重放 + 一致性复现（A-2）。
- 工具声明 `readOnly()`（默认 false）；非只读工具重放时被拦（`skipped=true, skipReason=NOT_READ_ONLY`）。

### 2.19 个人状态库（W6，地基已落地）

- **定位**：跨会话持续生长的**个人知识**（人 / 地 / 物 / 偏好 / 惯例 / 事实），带溯源，是 [2.20 事件与触发引擎](#220-事件与触发引擎规划迭代-4) 与 [2.21 主动执行与承诺闭环](#221-主动执行与承诺闭环规划迭代-4) 两层的数据地基。

- **单表落点**：`biz_memory_item`（V1.0.11）。同一 `(openid, kind, name)` 为一条生效事实，冲突时**新值覆盖旧值**（旧行转 `SUPERSEDED` 并保留 `supersedes_id` 链），重复提及则 `hit_count + 1 / last_seen_at` 刷新——覆盖与强化皆可回溯。

  - `origin`：`AUTO_EXTRACT`（已用）/ `TOOL`（**预留未启用**，工具主动写入待 W8 的 `remember`）。
  - **溯源**：`source_session_id` + `source_trace_id` + `extractor` + `confidence`。溯源指向会话与编排链路而非微信 MsgId——编排层看不到接入层 MsgId，且 `wx_message` 无 `trace_id` 列，故不设 `source_msg_id`（不留填不上值的列）。
- **生长管道**：编排器成功产出终态回复后发布 `MemoryGrowthNotice` → `MemoryGrowthListener`（自带**单线程 + 64 队列**的守护线程池）→ `LlmMemoryExtractor`（约束式 JSON 抽取，5s 超时，token 计入 `CostBudgetService`）→ `MemoryStore.upsert`。队列满即丢弃并计数（`droppedCount()` 可查），**不背压、不阻塞用户链路**。
- **召回注入**：`MemoryRecallService.buildRecallBlock(openid)` 以一条 `system` 消息注入本轮上下文（自带上限：条数 + 字符数，越界即截断），块内首行明示「不得据此编造已执行的动作」，与 BR-04 / 一致性校验语义保持一致；召回失败**放行不阻塞**（fail-open）。
- **热配置（`sys_config`，V1.0.12 播种）**：`memory.growth.enabled`（**默认 false**）、`memory.growth.max-items`（默认 5）、`memory.recall.enabled`（默认 true）、`memory.recall.max-items`（8）、`memory.recall.max-chars`（600）。生长默认关闭是因为它按消息计费地增加一次模型调用（G-32/G-33「预留未启用」口径）；召回只多一次索引读，故默认开启。**只开召回不等于状态库在用**——库空则召回为空。

- **隔离**：所有读写以 `openid` 为强制条件（BR-07）；日志中的 openid 经 `MaskUtils` 脱敏（BR-21）。
- **代码落点**：`domain/memory`（`MemoryWrite` / `MemoryFact` / `MemoryStore` 端口）、`application/memory`（抽取 / 监听 / 召回）、`application/admin/MemoryAdminService` + `interfaces/admin/MemoryController` + `interfaces/dto/memory/MemoryItemVO`（W6-b 后台）、`infrastructure/persistence/{entity,mapper,repository}`、`common/enums/Memory{Kind,Status,Origin}`。

### 2.23 灰度开关与熔断回滚（FR-22 / W2，已实现）

- **定位**：灰度是**叠加在功能主开关之上的第二道闸门**——主开关关闭时灰度不参与判断。因此新增灰度项**不改变任何既有行为**：`gray.<功能>.percent` 播种为 **100**（等同灰度上线前），"放量"这个动作是管理员把它调成 1/5/20，而不是"打开灰度"。**置 0 是一刀切**（白名单同时失效），否则 FR-22 异常流「回滚后行为恢复到变更前」（AC③）无法成立。
- **配置键（`sys_config`，V1.0.13 播种 7 项，category=`gray`）**：`gray.memory_growth.percent`（0~100）、`gray.memory_growth.whitelist`（逗号分隔 openid，仅比例 > 0 时参与）、`gray.breaker.enabled`（默认 true）、`gray.breaker.window-minutes`（5）、`gray.breaker.min-samples`（20）、`gray.breaker.error-rate-percent`（30）、`gray.breaker.p95-ms`（**0 = 该判据不启用**）。
- **分流判定顺序**（`GrayReleaseService.decide`）：openid 缺失 → `MISSING_OPENID` 不命中 → 比例 ≤ 0 → `GRAY_OFF` → 比例 ≥ 100 → `FULL_ROLLOUT` → 白名单命中 → `WHITELIST` → 稳定分桶 `bucket < percent` → `PERCENT` / `NOT_IN_GRAY`。**分桶用 SHA-256(`代号#openid`) 前 4 字节 mod 100**，不用 `String#hashCode()`：前者跨 JVM 稳定，是「同一用户恒定同一桶」（AC① 抽样 ±2% 的前提）与「改比例只放量、不洗牌」（单调放量）的最低实现；盐值取功能代号，避免同一批用户在不同功能上完全同桶。配置越界时读取侧按 0 处理并告警（写入侧已先拦）。
- **端点**（`interfaces/admin/GrayController`）：`GET /api/gray/status`（`hasAnyRole('SUPER_ADMIN','OPERATOR','AUDITOR')`，BR-23 只读口径）聚合各功能比例 / `whitelistSize` / `closed` + 熔断阈值（含 `checkIntervalSecond=30`）+ 近窗健康度实测；`GET /api/gray/preview?feature=&openid=`（同口径，代号不存在返回 10002）用于自证「同一入参必得同一结果」，出参 openid 经 `MaskUtils` 脱敏；`POST /api/gray/rollback`（`hasRole('SUPER_ADMIN')`，reason 必填 BR-25）一键回滚。**改比例与白名单仍走 `PUT /api/configs`**——刻意不新增第二套写入口，从而天然继承 FR-18 的值域校验、缓存失效与逐项审计。
- **写入校验（异常流 2a）**：`ConfigAdminService` 对 `gray.*.percent` 后缀键强制 0~100，越界（101 / -1）拒绝并回 `10002`；`gray.*` 下未播种的键按「配置项不存在」拒绝，杜绝凭空造灰度项。
- **熔断回滚**（`GrayCircuitBreaker`，`@Scheduled` 每 30s，单次评估只跑两条聚合查询）：判据为「窗口内 **L2~L4** 异常数 / 链路轮次」超错误率阈值，或链路 P95 时延超阈值（阈值 0 视为不启用），且窗口轮次 ≥ `min-samples`；任一越界即把**全部**在放量功能比例置 0，30s 内热生效（**AC②「≤60s」满足**）。分子**排除 L1**（接入层验签失败/重投多由外部探测造成，计入会让一次回调风暴误触发全局回滚）；**样本不足不回滚**（低峰期一条异常不应清零放量）。告警分级：真实回滚打 ERROR；越界窗口未过但已无在放量功能时降为 WARN，避免每 30s 一条重复告警把真告警淹没。
- **回滚复用而非另建**（`GrayRollbackService` → `ConfigAdminService.update`）：于是一次回滚自动获得值校验、`configCacheService.invalidate`（免重启）、逐项 `CONFIG_UPDATE` 审计，并额外补一行 `reg_type=GRAY / action=ROLLBACK` 汇总审计（记录回滚前明细 `代号=原比例` 与触发原因），使「因何回滚」与「改了哪些键」同行可比对；系统自动回滚时 `admin_id`/`ip` 为 NULL，与人工回滚可区分。**白名单不在回滚范围内**（置 0 后已不生效，保留名单值便于事后仍可看出放量计划）。
- **接线现状**：`memory.growth.enabled`（功能主开关，W6）之外再叠加 `GrayReleaseService.isHit(MEMORY_GROWTH, openid)`——生长按用户小步放量，因为它是"每轮多一次模型调用"的成本型功能（G-32/G-33 口径）。受灰度治理的功能清单用枚举 `GrayFeature` 而非运行时注册表：**新增灰度项须过评审**（新增即意味着熔断回滚会覆盖它）。
- **口径的边界（如实声明）**：① 异常与链路表只存**脱敏** openid（BR-21），异常未按功能归因，因此熔断是**全局健康度杀开关**而非"谁坏了关谁"——这与 BR-31「宁可误关不可漏关」一致，但不是细粒度归因，后者需要按功能埋点；② FR-22 基本流的**多 Prompt A/B 并行与效果对比看板**未实现（见 §7.13 未取得证据）；③ 后台**灰度观测台/放量控制台前端页**尚未做（当前以 `PUT /api/configs` 写、`GET /api/gray/status` 读），排在 W2-b。
- **代码落点**：`application/gray/{GrayFeature,GrayReleaseService,GrayHealthMetrics,GrayHealthSnapshot,GrayCircuitBreaker,GrayRollbackService}`、`infrastructure/gray/GrayHealthMetricsImpl`、`interfaces/admin/GrayController`、`interfaces/dto/gray/{GrayStatusVO,GrayPreviewVO,GrayRollbackRequest,GrayRollbackVO}`、`MaskingAssembler.toGrayPreviewVO`、`ConfigKeys`（7 键）、`ConfigAdminService`（灰度键值域校验）、`resources/db/migration/V1.0.13__seed_gray_config.sql`；测试 5 类 30 例（`gray/GrayReleaseServiceTest` 9 / `gray/GrayCircuitBreakerTest` 7 / `gray/GrayRollbackServiceTest` 4 / `interfaces/admin/GrayControllerTest` 5 / `infrastructure/gray/GrayHealthMetricsImplTest` 5）+ 既有用例扩充（`ConfigAdminServiceTest` 值域 2 例、`MemoryGrowthListenerTest` 灰度回滚停生长 1 例）。**无新表**（只读 `log_orchestration_trace` + `log_anomaly_event`，写入 `sys_config` + `log_audit`）。

### 2.24 工具插件化扩展接口（FR-23 / W3，已实现）

- **要解决的问题**：工具名一旦成为**封闭枚举**，"插件化"就是假的。W3 前有三处按工具名硬编码的派生口径——反幻觉判定词表（`ActionClaimExtractor.SEMANTIC_KEYWORDS`）、监控看板归因域（`MonitorService.mapToolToIntent`）、任务会话意图（`TaskSessionServiceImpl.TASK_INTENTS`）。新增一个工具要同时改这三个业务模块，等于没有扩展接口。
- **契约（`domain/tool/Tool`）**：在原有 `name()/description()/parametersSchema()/execute()` + `idempotent()/critical()/readOnly()` 之外，新增三件**默认方法形式的自述元数据**，全部向后兼容（既有工具不实现也能启动，BR-32）：
  - `Set<String> claimKeywords()`（默认**空集**）——本工具"声称完成"时的判定词。默认空集是**安全侧**选择：漏声明只会少一道校验，绝不会反过来把正常回复误判成幻觉。
  - `String monitorDomain()`（默认 **`chat`**）——看板归因域。默认落在既有的"未归因"桶，**不凭空造域**。
  - `IntentType taskIntent()`（默认 **`null`**）——任务会话的话题切换意图。`null` = 该工具不参与话题切换判定（保守默认）。
- **反查唯一入口（`ToolRegistry`）**：`claimKeywordsOf(name)` / `claimKeywordUniverse()` / `monitorDomainOf(name)` / `taskIntentOf(name)`。三处消费方**只按名反查注册表**，不再持有工具名的副本；未注册名一律回落契约默认值。
- **启动期 Fail-Fast（SRS 异常流 1a / 1b）**：`ToolRegistry` 构造时逐项校验，任一违规**直接阻止启动**并给出可定位到实现类的中文说明：
  - Schema 为空 / 无法解析 / 根节点缺 `type` / 某参数缺 `type` / `required` 引用未声明参数 → `工具参数 Schema 非法，启动终止: {name}（{实现类}）→ {逐条违规}`。
  - 参数名重复 → 由 Jackson `StreamReadFeature.STRICT_DUPLICATE_DETECTION` 在解析期检出（默认行为是静默保留后者，正是 SRS 要点名的隐患）。
  - 工具名冲突 → 提示**冲突双方实现类全名**；工具名不合法（非小写下划线）→ 同样附实现类。
- **零侵入的实证载体**：`QueryWeatherTool` 是刻意留下的"活样本插件"——新增它时，**对话引擎 `AgentOrchestratorImpl` 与 `resources/prompt/**` 零改动**（diff 为证，AC①），工具发现、参数下发、调用执行、审计落表、看板归因全部自动到位。需要澄清的是：本轮为了让这种零改动成立，先把三处派生口径的消费方（`ActionClaimExtractor` / `MonitorService` / `TaskSessionServiceImpl`）从「按工具名硬编码」改成了「注册表反查」——**这是一次性成本**，此后新工具不再触碰它们。接入面因此收敛为「1 个类 + 1 条配置」。
- **那条"配置"= FR-18 的工具开关**：`sys_config` 的 `orchestration.disabled-tools` 加一个名字即可（V1.0.14 把 `query_weather` 默认加入该清单 = **暗启动**）。刻意复用 FR-18 的开关与热生效，不新增第二套写入口；代价是"默认禁用"要靠迁移播种，而不是代码里的静态兜底。
- **口径的边界（如实声明）**：
  1. `IntentType` 仍是封闭枚举，**不占既有意图的插件只能吃 `taskIntent()=null`** 的保守默认（不参与话题切换判定）。彻底解开需要把意图本身开放注册，属后续工作。
  2. "1 个类"是字面成立的，但**让模型真的去调用它**还需要 Mock 脚本数据（`mock/llm-scripts.yml` 的 2 条规则）——那是测试替身，不是引擎或 Prompt；接真实模型时由模型自行选择。
  3. SRS FR-23 的**备选流 2a（工具分组 / 按角色授权）与 4a（工具级限流）本轮未实现**（见 §7.7 未实现项），当前只有全局 `orchestration.disabled-tools` 一刀切。
- **代码落点**：`domain/tool/{Tool,ToolRegistry,JsonSchema}`、`domain/tool/impl/*`（五件既有工具补自述 + 新增 `QueryWeatherTool`）、`application/safety/ActionClaimExtractor`、`application/admin/MonitorService`、`application/task/TaskSessionServiceImpl`、`resources/db/migration/V1.0.14__dark_launch_weather_tool.sql`、`resources/mock/llm-scripts.yml`；测试新增 4 类（`domain/tool/ToolRegistryTest` 11 例、`domain/tool/JsonSchemaTest` 8 例、`application/safety/ActionClaimExtractorTest` 4 例、`verification/QueryWeatherToolTest` 5 例）+ 夹具 `support/ToolRegistries`（离线构造生产工具集，避免测试另抄一份词表）。
- **证据等级**：A 级（代码 + 单测 + 全量 `mvn clean verify` **485 测试全绿**；干净库 `clawbot_w3` 冷启动、AC② 非法 Schema 真实启动失败、AC③ 日志 + `log_tool_call` + 看板归因域实证见 §7.14）。

### 2.25 成本与配额治理看板（B-4 / W5，已实现）

- **要解决的问题**：FR-20 ③ 的成本保护此前**只有一把 Redis 计数桶**——它能决定"要不要降级"，却答不出"钱花在哪了"（哪个用途、哪个模型、哪个用户、哪一次调用）。FR-17 AC① 又要求"看板上每个数字可核对"，没有明细表就无从核对。需求规格的前置条件「`LlmClient` token 计量落地」经 W5 开工时核查确认**当时并未满足**（响应里没有 usage 回填、也没有落库通路），因此本轮**先补数据面再做看板**，而不是先做一块没有源的表。
- **数据面（`log_llm_call`，V1.0.15）**：逐次记录 `purpose` / `provider` / `model` / `openid`（写入侧即脱敏，BR-21）/ `session_id` / `trace_id` / `prompt_tokens` / `completion_tokens` / `total_tokens` / `created_at`；四条索引按看板的四条检索路径建（`idx_llm_call_created_at` / `_openid_created` / `_purpose_created` / `_model_created`），不建冗余单列。
  - `total_tokens` 一律由 **prompt + completion 推导**，**不采用 provider 回报的 total**：明细与日预算必须同一算法，否则 FR-17 AC① 要求的"明细 ↔ 计数"互查永远对不上。
  - 用途口径为封闭枚举 `LlmCallPurpose`（`CHAT` 对话编排 / `MEMORY_EXTRACT` 状态库抽取 / `INTENT` 意图分类）。看板"按用途"分组时**枚举成员恒定在前、库中未知值追加在后**，避免"某天占比 100% 落在一个看不见的桶里"。
  - Mock 通道同样计量：`MockScript` 回填 token，使"零真实供应商"环境下也能验证闭环。
- **单一写入点（同源保证）**：明细与预算计数共用 `CostBudgetServiceImpl.recordLlmCall(LlmCallUsage)` 一个调用点，一次调用**两条口径同时前进**。两条写入口径**分开兜底**——DB 故障不使预算漏计，Redis 故障不使明细丢失；两者都只 WARN，绝不反向影响回复（best-effort）。
- **聚合面（`/api/cost/*`，只读）**：`overview`（今日/本月固定口径 + 生效预算 + 降级状态）、`trend`（按天/按小时桶）、`by-purpose`、`by-model`、`top-users`、`recent`（明细抽样，页面上直接附**等价 SQL**供复核）。鉴权沿用后台既有同构口径：六个端点逐个标 `@PreAuthorize("hasAnyRole('SUPER_ADMIN','OPERATOR','AUDITOR')")`（与监控/状态库一致），前端菜单与路由则用权限码 `cost:view`（三角色均授予）；读侧沿用 `QueryWrapper.select(...)+selectMaps` 聚合范式，`top-users` 与 `recent` 的 `limit` 在服务端夹紧到 **1..50**（`MAX_TOP_USERS`，防"顺手拉全表"）。
- **双口径同屏（本轮刻意设计）**：概览同时给出 `usedPercent` + `status`（**DB 明细**聚合判定）与 `counterUsagePercent` + `degraded`（**Redis 计数桶**，即降级动作实际所用者）。两者正常应当一致，Redis 被清空后计数桶会归零而明细仍在——把差异摊在界面上（"降级判定实际所用：4%"）而不是藏起来，口径漂移才是可见的。**代价是四个字段可能两两不自洽**（例：明细口径已到 DEGRADED 而 Redis 桶未满），界面因此同时显示"状态标签"与"降级标签"，不做二选一的掩盖。百分比分母取 `dailyTokenBudget()`，与降级判定**同一个**运行时预算值，杜绝"进度条未满 100% 却已降级"。
- **新表立刻进合规环**：`log_llm_call` 一落地就并入既有的两条清理通路（不是先建表后补合规）——FR-19 每日清理按 `LLM_CALL_RETENTION_DAYS=180` 删除过期明细，用户删除/匿名化按**脱敏形态**的 openid 匹配本表（传原文会命中 0 行，故调用点先 `MaskUtils.openid()` 再删）。本表只存脱敏标识与 token 计数，**不含对话内容**。
- **配置面**：`rate_limit.*` 三项播种进 `sys_config`（V1.0.16：`daily_token_budget=200000` / `max_message_length=2000` / 空白名单，**播种值与代码默认常量逐项相等 ⇒ 既有行为零变更**，只是把隐藏值变成可见可改），走 FR-18 的在线配置通路——**免重启热生效**、改动落 `log_audit`；值域校验拒绝 `0` 与负数（`budget≤0` 的语义是"无上限"而非"全降级"，一次误配即静默关掉成本保护，见 §7.5 D12）。阈值调低/调高都即时作用于下一条消息。
- **降级判定实时化**：`isDegraded()` / `dailyUsagePercent()` 改为**按"今日计数桶 / 当前生效预算"实时计算**，不再读粘滞的 `cost:degraded` 标志位（该标志位退为"同一状态只告警一次"的日志去重）。缺陷背景与复验见 §7.5。
- **前端**：`views/cost/index.vue` + `components/charts/CostTrendChart.vue`（输入/输出堆叠柱 + 调用量折线）+ `CostPurposeChart.vue`（token 占比饼图）；区间与粒度只作用于趋势/分布/排行/抽样，概览明确标注为固定口径；阈值调整**不在本页**，页面文案直接指向系统配置的 `rate_limit` 分组（避免第二套写入口）。openid 由后端脱敏后原样透出，前端**不再二次打码**；`model` 为空显示"供应商默认"。
- **口径的边界（如实声明）**：
  1. 计量单位是 **token，不是金额**——没有单价表，因此不做 ¥ 折算，也不宣称能看出 token 之外的任何成本。
  2. **视觉（`RecognizeImageTool`）与语音通道本轮不计成本**（其 LLM 调用不经统一计量入口）。
  3. 真实 provider 的 usage 回报**未测**（本机仍跑 Mock 通道）；接真实模型时"total 由 prompt+completion 推导"的口径保持不变。
  4. `INTENT` 目前仅被 `TaskSessionServiceImpl` 的话题切换判定调用，微信主链路不触发，故运行期无 INTENT 样本（枚举在前规则仍有效，显示为 0）。

- **证据等级**：A 级（全量 `mvn clean verify` **513 测试全绿** / 0 Checkstyle 违规；干净库 `clawbot_w5` 冷启动 + 运行期 FR-17 AC① 明细↔聚合↔SQL 逐项对上 + 预算热生效与降级实时跟随实证见 §7.15）。

### 3.8 关键运行时机制

| 机制 | 说明 |
|---|---|
| Agent Loop | 多轮工具编排受轮次/并发/超时硬约束（SC-01~SC-05）；未注册工具判 NOT_EXECUTED |
| 先回执后推送 | 回调 ≤700ms 回执，终态异步推送（BR-06） |
| 执行一致性校验 | 声称成功但无执行记录 → CLAIM_UNSUPPORTED 拦截 |
| 内容安全 Fail-Closed | 词库不可用时按 Fail-Closed 处理 |
| 配置热生效 | 运行时读取，改后免重启 |
| 回放护栏 | 非只读工具干跑重放时跳过 |
| 多模型路由 | 运行时 `llm.provider` 路由，缺实现回退 + 告警 |
| SSE 观测通道 | 编排事件入环形缓冲（100），`Last-Event-ID` 续传 + 心跳；`?token=` 回落鉴权（FR-08） |
| 链路时序埋点 | `System.nanoTime()` 记起点，逐 span 记录并落表；超预算标 `exceededBudget`（A-5） |
| 任务会话续接 | 追问建任务 → 槽位填充优先于全量重识别；≤3 次放弃、10min 超时清理（FR-24） |
| 限流 Fail-Open | 限流组件异常时放行，避免误伤正常请求（FR-20） |
| 数据保留清理 | 180 天定时清理 + 细粒度删除 + 匿名化（FR-19）；状态库仅清理已覆盖历史，生效事实不自动过期（W6） |
| 状态库生长 / 召回 | 每轮成功对话后异步抽取（独立线程池，队列满即丢弃）；召回以一条 system 块注入本轮上下文，失败放行（W6，见 §2.19） |

### 5.2 后端启动（local profile）

```bash
cd backend
SPRING_PROFILES_ACTIVE=local \
DB_HOST=127.0.0.1 DB_PORT=3306 DB_NAME=clawbot DB_USERNAME=root DB_PASSWORD=1234 \
REDIS_HOST=127.0.0.1 REDIS_PORT=6379 \
WX_TOKEN=clawbot-local-token ADMIN_INIT_PASSWORD=Admin@123456 \
java -jar target/clawbot-backend.jar
```

- 须显式设置 `SERVER_PORT`（如 8080），避免被运行环境注入的同名变量占用。
- 前端 `npm run build` 后由静态服务承载；开发态可跑 Vite dev server。

### 5.3 迁移与启动校验

1. Flyway 启动时自动执行 `db/migration`（V1.0.0 ~ **V1.0.16**），全 `success=1` 方可启动。
2. `GET /actuator/health` 返回 200、`status:UP`（db / redis / diskSpace 全 UP）。
3. 启动日志须出现 `ToolRegistry 初始化完成，已注册工具数=...`；该行为**工具契约校验通过的信号**——任一工具 Schema 非法或重名会在这一行之前直接终止启动（FR-23，§2.24）。
4. 改 `db/migration` 文件名后必须 `clean package`，避免残留陈旧脚本（Maven 资源增量复制不删除旧文件）。

### 5.4 Docker 编排（可选）

- `docker-compose.yml` 中 mysql 映射 `${DB_PORT:-3306}:3306`，与本机 MySQL84 冲突。
- 恢复二选一：先 `net stop MySQL84`；或改 `.env` 的 `DB_PORT`（如 13306）。
- Docker MySQL 初始口令由 `MYSQL_ROOT_PASSWORD` 决定（默认 1234），与本机库数据不互通。

## 第 6 章 维护指南

### 6.1 冷启动验证（结项必做）

- **教训**：单测全绿 ≠ 应用能启动。多构造器 Bean 未标 `@Autowired` 会在 `java -jar` 时失败。
- 结项前必须执行一次真实 `java -jar` 冷启动，确认 `Started ... in Xs` 且 `/actuator/health=200`。

### 6.2 已知启动级坑

| 现象 | 根因 | 处置 |
|---|---|---|
| 启动即 `NoSuchMethodException` | 多构造器 Bean 未标 `@Autowired` | 生产构造器加 `@Autowired` |
| Flyway 1064 语法错误 | 用了 MySQL 不支持的 `CREATE INDEX IF NOT EXISTS` | 改普通 `CREATE INDEX` |
| Flyway 拒绝继续 | `flyway_schema_history` 残留 `success=0` | 删除该行后以修正脚本重试 |

### 6.3 日志与诊断

- 限流 / 审计 / 工具调用均有落表，可用 SQL 检索。
- 避免直接 `tail` 含敏感串（token / 口令）的日志（触发安全审批拦截）；用 `grep -c` 只取计数。
- 多模型路由 `provider()` 可查真实生效模型。

### 6.4 端到端走查

```powershell
powershell -File scripts/e2e-smoke.ps1 -AdminPassword Admin@123456
```

- 脚本须 **UTF-8 带 BOM**（PS 5.1 兼容）；已弃用 `-SkipHttpErrorCheck`（PS7 专属），改用自写 `Invoke-WebRequestSafe`。
- AC-E3（OPERATOR 越权 403）需 `-OperatorToken` 补 token 重跑。

### 6.5 后端进程管理

- 进程存活判定以 `netstat :8080 LISTENING` 的 PID 为准，不能只看 `health=200`（可能命中遗留旧进程）。
- 清理遗留进程用 PowerShell `Stop-Process -Id <pid>`。

### 9.6 坑位速记（本机实测）

- **Maven 启动器**：本机 `mvn` 脚本在 Git Bash 下因 `MAVEN_HOME` 解析为 unix 路径导致 `找不到 Launcher 类`。可用 Windows 风格路径直接调 java 引导：`java -Dfile.encoding=UTF-8 -cp "D:/apache-maven-3.9.15/lib/boot/plexus-classworlds-2.9.0.jar" -Dclassworlds.conf="D:/apache-maven-3.9.15/bin/m2.conf" -Dmaven.home="D:/apache-maven-3.9.15" -Dmaven.multiModuleProjectDirectory="<backend 绝对路径>" org.codehaus.plexus.classworlds.launcher.Launcher -B -o clean verify`。**离线 `-o` 现已可用**（本地仓库已含 `spring-boot-starter-parent:3.3.4`，实测全量 verify 通过）；`-Dfile.encoding=UTF-8` 必带，否则中文编译错误信息显示为乱码，掩盖真实报错。
- **D8 教训**：单测全绿 ≠ 能启动；多构造器 Bean 须显式 `@Autowired`；结项前必做 `java -jar` 冷启动（W4 为单构造器，已规避）。
- **Flyway**：`CREATE INDEX IF NOT EXISTS` 在 MySQL 报错，改普通 `CREATE INDEX`；改迁移文件名须 `clean package`。
- **`test-compile` 会骗人**：增量状态可能报 `Nothing to compile — all classes are up to date` 而漏掉构造器参数个数变更导致的测试编译失败；**结项信号只认 `clean verify`**。
- **curl 传中文报文（JSON 与 XML 同样中招）**：Git Bash 下把中文直接拼在命令行会被 Windows 代码页转码——`curl -d '{"reason":"中文…"}'` 表现为后端 `10002 参数格式非法`，微信 XML 报文则表现为**落库内容变成 U+FFFD 替换符**（`SELECT HEX(LEFT(content,6))` 见 `EFBFBD` 即可确诊），连带让按中文子串匹配的 Mock 规则**永不命中**、看起来像"插件没生效"（W3 取证实踩，§7.14）。可靠做法：报文写成 UTF-8 文件再 `curl --data-binary @file`，或改用 PowerShell 发体（`e2e-smoke.ps1` 内部显式按 UTF-8 取字节，不受影响）。
- **端口被别的项目占用**：本机 8081 可能被其他项目的 jar 常驻（`netstat -ano | grep :8081` + 查 PID 命令行确认）。**不要停别人的进程**，取证改用 `SERVER_PORT=8092` 之类，并在证据记录里写明实际端口。
- **终端乱码 ≠ 库内乱码**：`mysql` 客户端在 Windows 控制台输出中文为乱码时，用 `SELECT CHAR_LENGTH(col), LENGTH(col)` 判定（UTF-8 汉字应为 1 字符 / 3 字节）再下结论。
- **管理员口令未知**：不要重置或猜测既有库口令；新建空库 + `ADMIN_INIT_PASSWORD` 播种全新 superadmin 是取得 AC-E1/E3/C1 证据的可复现做法（§7.10）。
- **日志/口令**：`tail` 含 token/口令的日志会触发审批拦截，用 `grep -c` 取计数。
- **前端**：勿走 npm shim（managed node 会拉 wsl 被拦），直接 `node.exe node_modules/<pkg>/bin` 调用；`vue-tsc`/`vite`/`eslint`/`vitest` 同理。
- **浏览器验证须用 `http://localhost:5173`**：后端 `clawbot.cors.allowed-origins` 默认只放行 `http://localhost:5173`，用 `http://127.0.0.1:5173` 打开时页面能加载但**所有 `/api` 请求返回 `Invalid CORS request`**（表现为登录后仍停在登录页，易误判为产品缺陷）。例外：W5 实证时 5173 的 `[::1]` 栈被外部进程占用，遂以 `CORS_ALLOWED_ORIGINS='http://localhost:5173,http://127.0.0.1:5173'` 起 jar 并走 `127.0.0.1:5173`（**改的是启动参数，不是产品默认值**）。
- **本机浏览器截图不可得**：in-app browser 无可见视口时 `take_screenshot` 直接返回 `NATIVE_BROWSER_VIEWPORT_UNAVAILABLE`（`viewport=0x0, visibilityState=hidden`），但 `take_snapshot`（可访问性结构树）与 `list_console_messages` 仍可用 ⇒ 结构实证与控制台无错可查，**像素级视觉核对只能标"未取得证据"**。
- **前端 lint 基线**：`npm run lint`（`--max-warnings 0`）**是 CI 前端作业的第一步**，当前因历史文件 `views/monitor/console.vue` 的 31 条格式 warning 而**失败**（W5 时确认，见 §7.5 待处理项）。判断标准是**本次改动文件单独跑 eslint 干净**，同时如实记录该存量，不得因"不是我引入的"而把它写成已通过。
- **出网**：沙箱 `git push` **可能** `FATAL: Unable to connect to relay host, errno=10061` + `Connection closed by UNKNOWN port 65535`（`ssh -T git@github.com` 同样失败 ⇒ 是本机 SSH 代理中继没起来，不是仓库权限问题）。2026-09-21 上午/下午曾连续推送成功，晚间这轮 W5 连试 3 次全失败 ⇒ **间歇性**，遇失败先重试、并跑一次 `ssh -T` 定性。推送状态一律以 `git status -sb`（`ahead N`）与 `git log --oneline -1 refs/remotes/origin/main` 为准，不凭记忆写入本文档（§9.1 的"未推送"标注即由此得来）。
- **Vite 代理指向**：dev server 代理默认 `http://localhost:8080`（`vite.config.ts`），而本机 8080 常被占用、实证 jar 起在 8081——浏览器实证须用 `VITE_API_PROXY_TARGET=http://localhost:8081 npm run dev` 启动，否则 `/api/**` 全部落空。
